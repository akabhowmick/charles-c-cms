# A11Y Decisions Log (Pattern Memory)

> **Purpose:** cross-turn memory of choices between **equally conformant alternatives**. Two implementations can both pass `A11Y.md` and axe and still diverge (different `role`, focus pattern, announcement wording) — twenty compliant modals, zero coherence. This file prevents that.

## Rules for the AI

1. **Record only what is not derivable** from `A11Y.md` rules or from the code itself. Landmarks, headings, and alt presence are machine-verifiable — they do **NOT** belong here.
2. **Index by pattern, never by screen.** ✅ *"Destructive confirmation modal → `alertdialog`"* · ❌ *"The dispute modal does X"*.
3. **One line per decision:** pattern → choice → short why.
4. **Read before building:** before generating any interactive component, check this log and reuse the recorded pattern (see *Component Reuse* in the AI Behavior Contract).
5. **Never fork silently:** if a new requirement contradicts a recorded decision, ask the user — do not create a parallel variant.
6. **Stay lean:** tens of lines, not hundreds. This file shares the context budget with Lazy Loading; if it grows past ~40 entries, consolidate.
7. **Versioned, never gitignored:** this is *shared* memory — across turns, agents and developers. A local-only copy per developer forks the patterns and defeats the file's entire purpose.

- **Lightbox / image dialog focus trap** (`Photos.tsx`) → manual `keydown` handler cycling `Tab`/`Shift+Tab` across `dialogRef.current.querySelectorAll('a[href], button:not([disabled]), [tabindex]:not([tabindex="-1"])')`, no headless-ui/focus-trap dependency added — consistent with the project's zero-extra-a11y-dependency style (plain React + Tailwind throughout). Initial focus lands on the dialog container (`tabIndex={-1}`, programmatically `.focus()`ed); focus returns to the trigger element on close via a `lastFocused` ref. Reuse this exact pattern for any future modal/dialog in this codebase instead of re-deriving a trap. (2026-08-08)
- **Card-as-stretched-link focus indicator** (`EventCard.tsx`) → when a native `:focus-visible` outline on the anchor itself would be visually confusing (the anchor is a "stretched link" covering a whole `<article>` card via `after:absolute after:inset-0`, so an outline on the anchor alone only rings the title text, not the card), show the ring on the parent card via `focus-within:ring-2 focus-within:ring-pine focus-within:ring-offset-2` on the `<article>` instead of suppressing focus outright. Chose `focus-within` over a `has-[a:focus-visible]` compound selector — both compile correctly in this project's Tailwind v4 setup, but `focus-within` is simpler, more broadly understood, and avoids the (harmless but confusing) 300ms `transition-all` cross-fade making the ring look absent when sampled synchronously. Trade-off: `focus-within` also rings briefly on mouse-click focus, not just keyboard — accepted, since the goal is "never suppress without a visible fallback," not pixel-perfect mouse/keyboard differentiation. Reuse this pattern for any other stretched-link card. (2026-08-08)
- **"Link that looks like a button"** (navigational CTAs sitewide) → never nest `<Button>` inside `<Link>` (produces `<a><button>`, a WCAG 4.1.2 nested-interactive-controls violation). Instead use `<Link to="..." className={buttonClasses({variant, size})}>` — `buttonClasses()` is exported from `src/components/ui/Button.tsx` and is the exact same class-building logic `Button` uses internally, so visual output is identical. `Button` itself is reserved for real `<button>` elements only (form submits, sign-out, cancel, destructive actions). Reuse `buttonClasses()` for any future "styled as a button" link instead of wrapping. (2026-08-09)
- **Design-token contrast fixes: new token vs. editing in place** → when a color token fails contrast in one usage context but is correctly compliant in another (e.g. `--color-taupe-light` is fine as light-on-dark text on `pine-deep` but fails as a border-on-white), add a **new** token (`--color-taupe-strong`) for the failing context rather than darkening the shared token, which would fix one usage while breaking the other. Only darken a token in place when *every* usage of it is in the same contrast direction (done for `--color-taupe`, which is only ever used as text-on-light). Check `A11Y.md` §4 (contrast) against **every** background a token appears on — including secondary backgrounds like `--color-paper-deep` — before considering a fix complete; the first darkening pass here missed the footer's `paper-deep` background and needed a second round. (2026-08-09)
